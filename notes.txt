along with js fundamentals required 

CLASS: blueprint used to create objects/instances.
INSTANCE: an actual object created from a class using new. Every instance is an object, but not every object is an instance of a particular class.
new User("Rahul"): creates a new User instance, runs its constructor, then assigns the resulting instance to user1.
constructor(): automatically runs when a new instance is created and initializes its properties.
this: refers to the current object/instance being worked on. Inside a constructor, this refers to the newly created instance, which is later assigned to a variable like user1.
extends: makes a child class inherit properties/methods from a parent class.
class Dog extends Animal: Dog inherits from Animal.
super(): calls the parent class constructor and initializes the parent part of the same child instance. It does not create a separate parent object.
throw: stops normal execution at that point and raises an error, which can be handled by catch/error handling.
class ApiError extends Error: creates a custom error class based on JavaScript's built-in Error class, allowing extra properties like statusCode.
PROMISE: a built-in JavaScript object that represents the eventual result of an asynchronous operation. States: pending → fulfilled (success) or rejected (failure).
new Promise((resolve, reject) => {...}): creates a Promise. The function passed to Promise is the executor function; Promise provides resolve and reject functions to it.
resolve(value): tells the Promise that the operation succeeded and provides its result.
reject(error): tells the Promise that the operation failed and provides the error/reason.
.then(): handles the successful result of a Promise.
.catch(): handles a rejected/failed Promise.
async: makes a function asynchronous and allows await inside it. An async function always returns a Promise.
await: waits for a Promise to settle inside an async function. If fulfilled, it gives the resolved value; if rejected, it throws the error. It pauses only that async function, not the whole JavaScript program.
const result = await promise: waits for the Promise to fulfill and stores its actual resolved value in result, not the Promise itself.
try/catch with await: try contains the awaited operation; if its Promise rejects, await throws the error and execution moves to catch.
Promise.resolve(value): creates/returns a fulfilled Promise containing value. Usually you don't create Promises manually because libraries/functions like Mongoose often return Promises themselves.
ASYNC HANDLER: A function that wraps an async request handler so rejected Promises/errors can be passed to Express error middleware.
Promise.resolve(requestHandler(req, res, next)).catch((err) => next(err))
requestHandler(req, res, next): the actual controller/route handler being executed.
Promise.resolve(): ensures the returned value is handled as a Promise. If requestHandler returns a Promise, it works with that Promise; if it returns a normal value, it converts it into a resolved Promise.
.catch((err) => next(err)): if the handler's Promise is rejected, pass the error to Express's next() so Express error-handling middleware can handle it.
WHY ASYNC HANDLER: Avoids writing try/catch in every async controller just to pass errors to Express.
CUSTOM API ERROR:
class ApiError extends Error {
    constructor(statusCode, message) {
        super(message);
        this.statusCode = statusCode;
    }
}
ApiError extends Error → custom error based on built-in Error.
super(message) → initializes the parent Error with the message.
this.statusCode → adds custom HTTP status information to the same error instance.
THROW:
throw new ApiError(404, "User not found");
Creates an ApiError and stops normal execution so the error can be handled by catch/error middleware.
EXPRESS ERROR FLOW:
Controller throws/rejects → async handler catches rejection → next(error) → Express error middleware handles the error.

User is used for methods available from mongodb or mongoose , for specific methods like check password , user is used 
 
JWT Authentication
Login → username/email + password → find user → verify password → generate access + refresh tokens → send secure cookies
User.findOne({ $or: [{username}, {email}] }) → find which account is trying to login | username OR email
Password check → proves user actually knows the password of that account → only after this should tokens be generated
Access Token → short-lived proof that user has authenticated → sent with future protected requests | JWT contains user _id
Refresh Token → used to generate a new access token when access token expires → longer-lived | stored in DB so server can control/invalidate the session
generateAccessAndRefreshTokens(userId) → helper gets userId → finds user → generates access + refresh token → saves refresh token in DB → returns both
Why find user again inside helper? → helper was designed to receive only userId and handle the user/token work itself | design choice, not fundamentally required → could instead pass the already-found user
user.refreshToken = refreshToken → attach refresh token to that user's document
user.save({ validateBeforeSave: false }) → save refresh token in MongoDB | validateBeforeSave: false → skip normal schema validation while saving this token update
JWT generation → _id is put inside JWT payload when token is created → token therefore carries the identity of the user
user._id → JWT payload → signed accessToken → browser
Later → accessToken → jwt.verify() → decodedToken → decodedToken._id
decodedToken._id → not created by jwt.verify() → _id was already put inside JWT during generation | verify() validates token and returns its payload
Cookies → browser stores authentication tokens → automatically sends them with future requests
httpOnly: true → browser can send cookie but JavaScript cannot directly read it
secure: true → cookie sent only over HTTPS
loggedInUser → find user again and .select("-password -refreshToken") → create safe user object for response | don't send sensitive fields
verifyJWT
verifyJWT → middleware that protects routes → verifies request is authenticated before controller runs
Request → accessToken → verifyJWT → verify token → get user ID → find current user → req.user → next() → controller
Token extraction → first check req.cookies.accessToken | otherwise check Authorization: Bearer <token>
jwt.verify(token, ACCESS_TOKEN_SECRET) → verify JWT signature + expiration → valid token → decoded payload | invalid/expired → reject request
decodedToken._id → ID carried inside JWT → tells server which user the token represents
User.findById(decodedToken._id) → get current user from DB → JWT tells us the claimed identity | DB tells us whether that user currently exists + gives current data
req.user = user → attach authenticated user's data to request → makes user available to controllers/middleware further down the chain
next() → authentication successful → continue to next middleware/controller
Why middleware? → authentication logic is reusable across multiple protected routes → keeps authentication separate from controller/business logic
Logout
verifyJWT → req.user → identify user → remove refreshToken from DB → clear cookies
Remove refresh token from DB → invalidate the user's refresh session → prevents using that refresh token to continue the session
clearCookie("accessToken", options) → remove access token from browser
clearCookie("refreshToken", options) → remove refresh token from browser
Repeated find
Login findOne() → Who is trying to login? → username/email → user
generateAccessAndRefreshTokens() findById() → helper only received userId → independently finds the user | mainly a function-design choice
verifyJWT findById() → JWT gives user _id → find the current user in DB → confirm user still exists + get current data
Flow → credentials → find user → verify password → generate tokens → store refresh token → send cookies → future request → verify access token → get _id → find current user → req.user → protected controller → logout/invalidate refresh session
